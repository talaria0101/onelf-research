# Comprehensive Systems Architecture Report: onelf Competitive Landscape, Internal Architecture, Ecosystem Failure Modes, and Strategic Roadmap

## 1. One-Paragraph Verdict: Where onelf Stands Today

**`onelf` (latest release 0.4.2, tag `0.4.2` = `e1a56af`, 2026-10-21; audited at source HEAD `cd99efb`, 2026-10-26, which is four unreleased commits past that tag) is a young (351 commits), technically careful single-file executable packaging engine for modern Linux. "Most elegant" is an opinion and this report does not measure it.** Statements below say whether they hold for the 0.4.2 release binary or only for HEAD. By fusing a static musl ELF runtime launcher (`onelf-rt`), a payload that is either independently zstd-compressed blocks (the default) or, since 0.4.2, a [stipplefs](https://github.com/QaidVoid/stipplefs) image deduplicated across files (`--payload stipple`), with 64 KiB BLAKE3 verification of the content in both cases (`onelf-format`), and an in-process ELF symbol-version resolver (`verdef.rs`, `resolve.rs`), it combines three things that no single competitor combines (Anylinux-AppImages also shares mounts between instances and has a fallback chain, so none of these is unique on its own): in-memory execution (`memfd_create`) for static single-binary packages only, a case the project's own docs say to ship directly (`docs/guide/introduction.md`), with no latency measured; a six-mode execution ladder whose last mode (persistent cache) is opt-in, so a dynamic app's default chain is four modes (userns FUSE, fusermount3 FUSE, userns tmpfs, rundir) and still runs with FUSE and user namespaces both unavailable if a writable directory on an exec-capable mount exists; and automated host GPU driver discovery without `LD_LIBRARY_PATH` pollution (plus, since v0.4.0, an automatic fetch of the recipe's pinned GL build when the host has none). Three limits stand out: nothing in the file authenticates its producer at launch (the hash chain is unkeyed by design and the project says so: `footer.rs:208-210`, `docs/guide/verify.md`; the detached Ed25519 signature is checked on self-update and by `onelf verify --key --sig`), it has no sandbox (a stated non-goal: `docs/guide/introduction.md`, "onelf isn't a sandbox"), and its sysroot builds are only reproducible when the recipe pins the sysroot archive by BLAKE3 hash (supported since v0.4.0, with provenance recorded in `.onelf/provenance.toml`); unpinned recipes drift with upstream images. Range-request (direct-release) delta updates, which the first edition of Section 6 proposed, are implemented at HEAD (PR #41, `cd99efb`) and are not in a release yet. Section 6 still proposes launch-time signature checking and in-process sandboxing. They are design proposals, and whether they would make onelf the premier format is not something this report can show. The earlier headline gap, package size against DwarFS, no longer holds for `--payload stipple` (Rank 3 and `measurements/README.md`).

## 3. Where onelf Already Wins (Backed by Verified Architecture)

The following competitive advantages are backed directly by inspected source code and verified architectural mechanisms:

- **True In-Memory Execution via `memfd_create` (Zero Filesystem Residue):**  
  For a package whose default entrypoint is a static single binary (or one packed with `memfd = true`; other entrypoints start at the next rung), `onelf-rt` decompresses payload blocks directly into an anonymous kernel memory descriptor created via `memfd_create("onelf", 0)` - no `MFD_CLOEXEC`, no seal/fchmod step - and executes `/proc/self/fd/<fd>` (`crates/onelf-rt/src/memfd.rs:14-28` and `main.rs:180-237` **[verified]**). It touches no host disk path, creates zero mount points and leaves no temporary files. No latency was measured. Limits on this win: it applies only to static binaries, which the project's own docs say to ship directly (`docs/guide/introduction.md`, "When not to use onelf"); the package tree is absent in this mode (`ONELF_DIR` is empty, `[paths]` is not applied); and a competitor's runtime is not required to leave files behind either way, since uruntime's own helper tools already run from memfd [read, not traced end to end].
- **Dynamic In-Process GPU/Driver Resolution Without `LD_LIBRARY_PATH` Pollution:**  
  Unlike legacy AppImages that set global `LD_LIBRARY_PATH` (which leaks into child processes and crashes `xdg-open` or host browsers), `onelf` parses `SHT_GNU_VERDEF` symbol version tables in ELF libraries (`verdef.rs:40-48` **[verified]**). It executes a symbol-version superset comparison (`resolve.rs:355-373` **[verified]**): if the host GPU library (`libGLX.so`, `libEGL.so`, `libvulkan.so`, `libcuda.so`, `libva.so`) provides all bundled versions plus newer ones, `Choice::Host` wins. `onelf-rt` materializes an ephemeral symlink farm containing only the winning host libraries (`resolve.rs:224-267` selecting, `materialize()` at `resolve.rs:689-722` **[verified]**; at HEAD the closure also seeds from `libGLX_*` and from what the host's DRI modules need, `resolve.rs:470-498`) and passes `--library-path` directly to the dynamic linker (`PR #31`, commit `1e5385e` **[verified]**).
- **The Most Resilient Execution-Mode Fallback Chain in Linux Packaging:**  
  `onelf-rt` implements a strict 6-rung execution ladder (`crates/onelf-rt/src/main.rs:169-370` **[verified]**):
  `Mode 1 (memfd) -> Mode 2 (userns FUSE) -> Mode 3 (fusermount3) -> Mode 4 (userns tmpfs) -> Mode 5 (ephemeral rundir) -> Mode 6 (persistent cache)`.
  If unprivileged user namespaces are blocked (the docs name Ubuntu 23.10+ AppArmor restrictions) and FUSE is missing (e.g. a stripped container), `onelf` steps down to runtime-directory extraction (`rundir.rs:26-160` **[verified]**). That needs a writable directory on an exec-capable mount: the 2026-10-18 smoke test failed this rung with EACCES because its `/tmp` was noexec, and the 2026-10-28 smoke test of the 0.4.2 release did the same here (`exec failed: Permission denied`); with `XDG_RUNTIME_DIR` pointed at an exec-capable directory the rundir rung ran, and so did the cache rung with `XDG_CACHE_HOME` set (observed, one tiny package, this host has no `/dev/fuse` and no user namespaces). The cache rung runs only on request, or first when the package was packed with `--prefer-cache` (0.4.2): then memfd is skipped, the cache is tried before FUSE, and a failed extraction falls through to the other rungs (`main.rs:181`, `main.rs:260-273`). Competitors fail differently: ralismark's nix-appimage stub exits 127 when `unshare` fails, while pkgforge's wrapper prints bwrap's error and exits 0 (`AppRun.sh:410-421`); Flatpak needs bwrap (setuid or userns) to start an app.
- **Automatic Kernel-Managed Teardown via Mount Namespaces:**  
  In primary FUSE mode, `onelf-rt` calls `unshare(CLONE_NEWUSER | CLONE_NEWNS)` and mounts `/dev/fuse` inside the private namespace (`fuse/mount.rs:120-146` **[verified]**). Because the mount is bound to the mount namespace, the kernel tears it down when the last process in the namespace exits, including after `SIGKILL` [documented in `docs/guide/execution-modes.md`; not exercised here]. This holds for the namespace rung only: on the `fusermount3` rung a killed server leaves a disconnected mount that the next launch of any package sweeps (same page). That AppImage's runtime leaves a mount directory behind on a crash is the onelf docs' own claim (`docs/guide/introduction.md` comparison table) [reported, not tested].
- **Concurrent FUSE Instance Sharing:**  
  When multiple instances of the same package launch concurrently, `onelf-rt` uses a shared lock file `.onelf-<name>-<id8>.share` and client leases (`crates/onelf-rt/src/fuse/share.rs`, `paths.rs:148-161` **[verified]**). Subsequent processes join the existing mount namespace (`setns(CLONE_NEWNS)`), avoiding redundant decompression and memory duplication **[verified: docs and `fuse/share.rs`]**. Anylinux's uruntime does the equivalent with OFD locks, so this is parity, not a differentiator.
- **Self-Contained Musl Runtime with no_std Rust Payloads:**  
  The appended bootstrap/env payloads are `no_std` Rust (`onelf-payloads`, workspace-excluded; `PR #28` **[verified]**), while `onelf-rt` itself is a normal std binary [corrected: an earlier edition called the whole runtime no_std]. `onelf` completely eliminated the fragile `onelf-preload` dynamic library interposer (`PR #26` **[verified]**), which avoids `LD_PRELOAD`. "High reliability across musl, glibc and static targets" is not measured here.
- **Cross-File Deduplicating Payload (`--payload stipple`, 0.4.2):**
  The packer can write the payload as a stipplefs image instead of per-file zstd blocks (`crates/onelf/src/pack.rs` `stipple_payload` at `pack.rs:1838`, `crates/onelf-format/src/payload.rs`, flag `STIPPLE_PAYLOAD = 1 << 9`, `footer.rs:109`). The manifest keeps one record per 64 KiB slice with its BLAKE3, so the runtime verifies stipple content exactly as it verifies a decompressed block (`payload.rs:1-11`, `read_slice` at `payload.rs:72-85`). The packer reads every file back out of the finished image to record the slices, so the manifest describes what the image holds, not what the source held (`pack.rs` comment on `stipple_payload`). On the three app trees measured here it takes the package from 4% to 27% above a DwarFS image to 0.7% to 1.5% above (Rank 3 and `measurements/README.md`). Costs found: a compressed stipple payload loses delta updates (below), `--dict` is rejected with it, and on a 0.4 MB test tree it was 7.6% larger than the blocks payload (see `measurements/README.md`).
- **Direct-Release Delta Self-Update (HEAD, unreleased):**
  PR #41 (`cd99efb`) replaces `zsync-rs` with an update URL that names the release binary itself; the runtime reads the footer and the manifest with two range requests and copies unchanged blocks from the running binary (`crates/onelf-rt/src/update/`). This is the first edition's Candidate 2, now built. See Candidate 2 for what is and is not verified.
- **Features the first edition did not cover:** shared dependency sets (a pinned Qt/GTK closure fetched once and mounted once for every package that names it, `docs/guide/sysroot.md`, in 0.4.0), restoring the caller's environment for host programs the app starts via `execve`/`posix_spawn` hooks in the injected `onelf-env` constructor (`docs/guide/environment.md`), and profile-driven block prefetch (`docs/guide/execution-modes.md`).

## 4. Where onelf Loses or Has Gaps (Ranked Strictly by User Impact)

The gaps below keep the first edition's order. No frequency or impact data supports that order, so read the numbers as labels, not as a ranking. Rank 1 in particular is weaker than its position suggests (see its entry).

```
GAP SEVERITY PYRAMID:
▲
│ [Rank 1] No launch-time authentication of the package (unkeyed hash chain, by design)
│ [Rank 2] Total Absence of Application Sandboxing by Default -> Malicious Ambient Authority
│ [Rank 3] Compression vs. DwarFS: closed by --payload stipple (0.7-1.5%); start-up unmeasured
│ [Rank 4] Build Sysroot Mirror Drift & Lack of Lockfiles -> Non-Deterministic Builds Over Time
│ [Rank 5] Hard Kernel Floor (Linux 3.17+ / 3.8+) -> Rejection on Ancient RHEL/CentOS
│ [Rank 6] Desktop shims: GTK Wayland app id not handled; env leakage and Fontconfig are handled
│ [Rank 7] Cross-package sharing only through opt-in dependency sets / cache mode
│ [Rank 8] Architecture Support Ceiling (x86_64, aarch64, i686 only) -> Open Issue #36
│ [Rank 9] Dynamic linker string patching (/XXX/) -> depends on glibc's loader strings (inferred)
│ [Rank 10] Incomparable Glibc Fallback Crash Mode -> Runtime Symbol Missing on Diverged Distros
▼
```

### Rank 1: No Launch-Time Authentication of the Package
- **Mechanism & Code:** In `crates/onelf-format/src/footer.rs:181-183` (struct at `footer.rs:162-184`; an earlier edition cited `footer.rs:56-65`, which is the flags block) (**[verified]**), the trailer integrity check is an unkeyed 32-bit checksum (`manifest_checksum: [u8; 4]` computed via XXH32). While individual 64 KiB blocks carry BLAKE3 hashes and self-update verifies an Ed25519 signature (`update.rs:81`), **there is no signature check performed at application startup on disk**.
- **What this is:** an integrity chain, not authentication. The source says so: "an integrity check, not authentication: whoever rewrites a file can recompute every hash in it. Only a detached signature proves who produced a package" (`footer.rs:208-210`), and `docs/guide/verify.md` repeats it. Payload blocks are BLAKE3-checked against the manifest on every read path, so corruption of payload bytes is caught at use; only a rewritten manifest with a recomputed XXH32 passes, and `onelf verify` additionally checks `prefix_hash` and `footer_hash`.
- **Why the severity is lower than the first edition said:** a party with write access to the file can replace the runtime ELF in front of the manifest, so an in-file check cannot defend against that party. The same party can replace any user-owned executable the user runs, with or without onelf. Launch-time signature checking helps only against a key the user obtained out of band. The existing detached-signature path (`onelf verify --key --sig`, self-update) already covers that case on request. At HEAD there is also a deliberate way out of signing: a package packed with `--update-unsigned` stores no key and its runtime installs whatever the update URL serves after content checks against the downloaded manifest, printing a warning on every update (`update/mod.rs:57-77`, `update/mod.rs:467`; the 0.4.2 release binary rejects the flag, observed). It is opt-in, HTTPS-only and visible, so it is a documented trade, not a hidden gap, but it moves trust for those packages entirely to the release server.

### Rank 2: Total Absence of Application Sandboxing by Default
- **Mechanism & Code:** `onelf-rt` spawns entrypoints with the full ambient authority of the invoking user (`crates/onelf-rt/src/launch.rs:1-60` **[verified]**). While it unshares user and mount namespaces to mount FUSE (`fuse/mount.rs:120`), it does not restrict network, IPC, PID, or filesystem access.
- **Concrete Failure Mode:** An untrusted or compromised GUI application packaged as an `onelf` binary has full unconfined read/write access to `$HOME/.ssh/id_rsa`, cloud credentials and browser cookies; an X11 client can also read other clients' input, which no filesystem sandbox prevents. (That enterprise teams would block such binaries is speculation, not a finding.) The project lists sandboxing as out of scope: "onelf isn't a sandbox; see bubblewrap or flatpak for that" (`docs/guide/introduction.md`). Flatpak's own sandbox is only as tight as the permissions an app requests.

### Rank 3: Compression Efficiency and Startup I/O Density vs. DwarFS (size gap closed for `--payload stipple`; start-up not measured)
- **Mechanism & Code:** The default payload is discrete zstd-compressed blocks (64 KiB, `compress.rs:15`, commit `6b08951` **[verified]**), identical files stored once (`pack.rs:1296`), an optional trained dictionary, and no cross-file dedup. Since 0.4.2, `--payload stipple` stores a stipplefs image instead (`pack.rs:1838`, `payload.rs`, commit `1512eca`), with content-defined chunk dedup, many files per 32 MiB compressed block and an x86 branch filter.
- **Measured here (2026-10-28, onelf 0.4.2 release binary, one host, one pack per cell, sizes include the 1.13 MB runtime prefix, `measurements/README.md`):** against a DwarFS L22 `-S26 -B2` image, the default blocks package is 27.0% larger on `/usr/lib/chromium` (164.87 MB against 129.80 MB), 27.0% on firefox and 4.2% on dbeaver. The stipple package is 0.7%, 1.3% and 1.5% larger (130.70 MB, 85.10 MB, 89.18 MB), and 20.7%, 20.3% and 2.6% smaller than the blocks package. So the first edition's headline gap (DwarFS 21.3% smaller) does not hold for stipple packages. It still holds for the default blocks payload, and the earlier explanation (the 64 KiB window) is consistent with what stipple changes: a 1 MiB block size alone took the blocks package to +13.1% on chromium.
- **Where it does not hold:** on trees of many small files DwarFS stayed ahead of stipple: `/usr/share/icons` (52,651 files) 10.7% larger and `/usr/lib/python3.14` (4,320 files) 4.9% larger, with the runtime prefix removed from the onelf side. Stipple was larger than blocks on one 0.4 MB tree. Stipple packs faster than blocks on chromium and firefox and slower on dbeaver (single runs, shared host).
- **Start-up is the open half:** decode paths measured without FUSE (warm cache, `--onelf-extract`) were not faster with stipple: whole tree 1.03 s against 0.79 s, nine small files 0.111 s against 0.011 s at the default 32 MiB image block. The author reports the opposite for the stipplefs FUSE mount (Blender: 0.73 s first launch against 0.50 s from a folder). This host cannot mount FUSE, so which of these predicts an app launch is unmeasured. The project documents the block-size trade for blocks packages (`docs/reference/recipe-schema.md:102-106`).
- **Trade found in source:** a compressed stipple package cannot delta-update (Candidate 2), `--dict` is refused with it, and the image size depends strongly on the image block size (firefox: 85.10 MB at 32 MiB, 91.85 MB at 1 MiB).
- **Concrete Failure Mode (competitor side):** `Anylinux-AppImages` uses DwarFS (default `-C zstd:level=22 -S26 -B2`, `appimagetool/src/config.rs:175`), which performs whole-file dedup plus segment dedup over the 2 most recent 64 MiB blocks (`-S26 -B2`). Upstream reports DwarFS bundles smaller and faster than SquashFS (their claim; no percentage is published in the tooling repos). Size was measured here against onelf, speed was not.

### Rank 4: Build Sysroot Mirror Drift and Lack of Cryptographic Lockfiles
- **Mechanism & Code:** `onelf-sysroot` resolves the dependency closure against the pacman database of the *materialized sysroot image* (`closure.rs:22-81`, **[verified]**), not live mirror metadata as an earlier edition claimed. Since v0.4.0 a recipe can pin `[sysroot] archive` (local path or HTTPS URL) with an enforced BLAKE3 hash (`recipe.rs:226-232`), and builds write `.onelf/provenance.toml` with the resolved name/version pairs (commits `8d25a74`, `d04162b`, `275b4a2`).
- **Concrete Failure Mode:** Without a pin, rebuilding the same `onelf.toml` after the sysroot image changes yields different output. With a pin, builds are reproducible; what remains missing is a per-package lockfile format comparable to `flake.lock` for pinless flows.

### Rank 5: Hard Kernel Version Floor (Linux 3.8+ / 3.17+)
- **Mechanism & Code:** Two of the six modes use `memfd_create` (Linux 3.17+) and unprivileged user namespaces (3.8+) (`crates/onelf-rt/src/memfd.rs`, `ephemeral.rs` **[verified]**). The runtime-directory mode needs neither, and a failing memfd call falls through silently (`main.rs`), so these are floors for particular modes, not for the whole runtime. The floor of the static musl Rust runtime itself was not established; no `statx` call exists in the tree. The project documents no kernel floor, and all of these are inferred from syscall use.
- **Concrete Failure Mode:** `Anylinux-sharun` embeds a ptrace/seccomp syscall emulation layer (`kernel_compat.rs` **[verified]**) that lets an Arch-built glibc closure (built with `--enable-kernel=4.4`) run on x86_64 kernels down to 2.6.17; it switches on automatically below 4.0 or when `statx` is missing. Whether `onelf` runs on RHEL 6 / CentOS 6 class kernels is untested [inferred only]: the FUSE and tmpfs modes would not work there, and the outcome would depend on the runtime-directory mode and on the runtime's own syscalls.

### Rank 6: Missing Battle-Tested Desktop Shims
- **Mechanism & Code:** Anylinux ships several desktop shims. Which of them onelf lacks, checked against the onelf docs and source:
  1. *GNOME Wayland App ID Mismatch:* Anylinux's `gtk-fix-nonsense.so` forces the GTK window class/app id to `$GTK_WINDOW_CLASS` (`Anylinux-sharun/lib/gtk-fix-nonsense.c:5,127`). onelf has no equivalent (no hit for `GTK_WINDOW`, `prgname` or `app_id` in `crates/`). Whether apps are affected without it was not tested.
  2. *Fontconfig:* Anylinux's quick-sharun hook points `XDG_CACHE_HOME` at `$HOME/.cache/AppImage-Cache` (`quick-sharun.sh:4150-4162`); that is a startup hook, not a shim library, and the crash claim is unsourced. onelf generates a `FONTCONFIG_FILE` that includes the host's `/etc/fonts/fonts.conf` plus the package's fonts (`docs/guide/environment.md`) and does not redirect the cache.
  3. *Environment Leakage:* onelf already handles this. The `onelf-env` constructor that `bundle-libs` injects defines `execve`, `execv`, `execvp`, `execvpe`, `posix_spawn` and `posix_spawnp`, and a program outside the package gets the caller's original environment back (`docs/guide/environment.md`, "Programs the app starts"). The first edition's claim that onelf lacks this was wrong. Anylinux's `anylinux.so` hooks six exec/spawn functions and acts only for targets outside `$APPDIR` (`anylinux.c:511-557`). Caveats the onelf docs give: `system()`, `popen()` and the `execl` family pass the app's environment unchanged.

### Rank 7: Cross-Package Sharing Exists Only in Opt-In Forms
- **Mechanism & Code:** Each `onelf` process spawns its own private FUSE mount namespace or extracts to tmpfs (`crates/onelf-rt/src/main.rs:169-370` **[verified]**).
- **Concrete Failure Mode:** If a user runs 10 independent `onelf` applications that each bundle their own glibc, GTK and WebKit, each holds its own decompressed pages. Flatpak's hardlinked OSTree checkout lets the kernel page cache share a runtime's libraries across apps on the same runtime branch (apps on different branches share only files whose content is identical). onelf has two answers the first edition omitted: shared dependency sets, where every package naming the same Qt/GTK set shares one download, one extraction and one FUSE mount, server and block cache (`docs/guide/sysroot.md` "Sharing a dependency set", in 0.4.0; needs `fusermount3`, else the set is copied), and opt-in cache mode, which hardlinks identical files across packages (`cache.rs:164,279,328`). Within one package, concurrent launches share one mount (`fuse/share.rs` [verified]). The remaining gap is default-mode packages that bundle their own copies. On disk, Anylinux reports 2.0 GiB (20 AppImages) vs 6.27 GiB (Flatpak) on Btrfs+zstd in its own test (`disk-usage-vs-flatpak.md` [reported by a competitor, not reproduced]), so the disk cost of not sharing is not obviously in Flatpak's favour. RAM sharing was not measured by anyone here.

### Rank 8: Multi-Architecture Support Ceiling
- **Mechanism & Code:** Release binaries and docs cover `x86_64`, `aarch64` and `i686` (`README.md:54`, `docs/guide/installation.md:6`; PR #29, PR #30, commit `7438f5a` **[verified]**). Issue #36 ("more arch support") is open, fetched 2026-10-19 **[verified]**.
- **Concrete Failure Mode:** [inferred, no build attempted] Other targets would fail: `build.rs` `expected_machine()` knows only those three `e_machine` values and `ulexec.rs` and the payloads cover the same three. (`build.rs:140` names `armv7l` and `riscv64`, but only to match Nix store path names, not as supported targets.)

### Rank 9: Dynamic Linker String Patching Fragility
- **Mechanism & Code:** In `crates/onelf/src/bundle/elf.rs:1070-1087` (**[verified]**), `onelf` binary-patches paths inside the bundled `ld-linux.so`: replacing `/etc/`, `/usr/`, `/nix/`, `/lib/` with `/XXX/`, and `/lib64/` with the length-preserving `/XXX///`, to prevent loading host `/etc/ld.so.preload`.
- **Concrete Failure Mode:** This approach matches `sharun`'s (`/etc` to `/KEK`). The first edition's "works reliably across glibc 2.31-2.40" has no source anywhere in the onelf tree and is removed. Fragility to future glibc releases is a plausible risk (the patch depends on strings inside `ld.so`), not an observed failure [inferred].

### Rank 10: Incomparable Glibc Fallback Crash Mode
- **Mechanism & Code:** In `crates/onelf-format/src/resolve.rs:355-373` (**[verified]**), if host glibc and bundled glibc symbol version sets are neither subsets nor supersets of each other, `verdef::compare` returns `Choice::Incomparable`.
- **Concrete Failure Mode:** [plausible, trigger unmeasured] For `libc.so.6` the code records `Incomparable` and keeps the bundle (`resolve.rs:322-340`). A chosen host driver that needs a glibc symbol version the bundled libc lacks would then fail to load by name. The docs state the same limit ("a launch that can do neither never takes the host's glibc", `docs/guide/concepts.md`). Whether real host/bundle pairs ever land in the incomparable case (neither symbol-version set contains the other) is not established; a newer host glibc takes the `Host` branch and brings its own loader.

## 5. Top 10 Killer-Feature Candidates for onelf

Each of the following 10 feature candidates has been architected to exploit concrete competitor gaps and ecosystem pain points while honoring onelf core invariants:

### Candidate 1: Content-Addressed Reflink Deduplication (`ioctl(FICLONERANGE)`)
- **What it is & Technical Mechanism:** An unprivileged CLI utility (`onelf dedup <dir>`) that deduplicates disk storage across multiple `.onelf` binaries on copy-on-write filesystems (Btrfs, XFS, bcachefs, OpenZFS). Because `onelf-format` segments files into discrete 64 KiB payload blocks with known BLAKE3 content hashes, `onelf dedup` scans files, identifies identical byte sequences, and issues `ioctl(dest_fd, FICLONERANGE, &clone_range)` system calls (`linux/fs.h` **[verified]**). **Design flaw in this mechanism:** `ioctl_ficlonerange(2)` says disk filesystems generally require offset and length to be aligned to the fundamental block size, and the onelf format has no alignment or padding (`git grep -i align` in `docs/reference/file-format.md` and `pack.rs` finds none): blocks are variable-length zstd output packed back to back after a runtime prefix of a different length in every package. Identical content in two packages therefore lands at unaligned offsets, and a block-granular clone could not share it. Making this work would need a format change (aligned, padded blocks), which costs file size. With the 0.4.2 stipple payload the argument is stronger, not weaker: file content lives in 32 MiB compressed blocks shared by many files, so no run of bytes in the package corresponds to one file's content (`payload.rs:1-11`).
- **Competitor Gap Exploited:** Disk sharing across packages. onelf already has hardlink dedup in opt-in cache mode and shared dependency sets (see Rank 7), so the gap is narrower than the first edition said.
- **User Value:** The first edition claimed "near zero" for shared libraries [unmeasured and unsupported; removed].
- **Rough Effort:** Small (S) as first stated, but the alignment problem above makes it at least a format change [estimate; the `reflink-copy` crate's range-clone support was not checked].
- **Architectural Fit & Kernel Floor:** Natural fit. Requires Linux 4.5+ on Btrfs/XFS. Leaves file layout intact; completely unprivileged.
- **Risks & Failure Modes:** Ineffective on ext4. Must gracefully report unshared block status.
- **Target Persona:** Power users, homelab operators, Steam Deck gamers managing dozens of portable apps.

### Candidate 2: Direct GitHub Release Delta Updates (HTTP Range Requests on Block Manifest) - IMPLEMENTED AT HEAD, NOT RELEASED
- **Status:** Built in PR #41 (merged 2026-10-26, `cd99efb`, CI green on that commit per `gh run view`). It is not in release 0.4.2 (tag `e1a56af` still uses `zsync-rs`); the open release PR #40 is for 0.4.3. Everything below about it is **read from source and docs**: no HEAD binary exists to run (no CI artifact, and building was out of bounds for this pass), and the update path needs an HTTPS release server this sandbox does not have.
- **What it does:** The update URL names the release binary. `update::range::probe` learns the size (a `HEAD`, or a one-byte `Range: bytes=0-0` when `HEAD` fails), then reads the 76-byte footer and the compressed manifest with two explicit single-range requests (`range.rs:343-430`; the manifest read is refused above 256 MiB, `range.rs:341`). Equal `package_id` means up to date (`update/mod.rs:244-247`). Otherwise `delta::assemble` copies every payload block whose content hash the running package also holds, fetches the rest (spans closer than 128 KiB are merged, `delta.rs:220`), writes the new binary to a staging file and verifies it (`update/mod.rs:551-652`). A block copied from the running binary is decoded and re-hashed first, and a mismatch turns that block into a download (`delta.rs:11-15`).
- **GitHub compatibility:** The design uses only explicit single ranges, which is what GitHub release assets accept. Re-observed 2026-10-28 with curl against the 0.4.2 asset: `Range: bytes=0-0` answered 206, `bytes=-76` and the multi-range `bytes=0-1,5-6` answered 501 (both via `-I`), and an explicit `bytes=7558108-7558183` returned the last 76 bytes, identical to `tail -c 76` of the downloaded file. Whether the updater's own redirect, `If-Range` and ETag handling works end to end against GitHub was not run.
- **Competitor Gap Exploited:** Removes the external `.zsync` file and the `zsyncmake` CI step. Publishing is the binary plus one detached `<name>.sig`, or the binary alone under the unsigned opt-in (`docs/guide/self-update.md`). The first edition's "200 MB Electron app takes 10-20 MB" was an invented figure and is removed; delta sizes depend on how much changes and were not measured.
- **Limits found in the source:**
  1. A compressed stipplefs payload cannot be delta-updated: its bytes are not stable across builds (the image retrains a dictionary every build), so the updater downloads the whole file and says so on stderr. Only `--payload stipple --no-compress` deltas, at slice granularity (`delta.rs:16-23`, `docs/guide/self-update.md`). This is a direct trade against the size win in Rank 3. Premise measured (`measurements/README.md`, one changed file in a 91 MB tree): 66% to 81% of the new compressed stipple package's bytes were not found in the old one at any block size tried, against 0.2% for blocks and 0.1% for a stored image. The updater itself was not run.
  2. `--dict` blocks payloads lose reuse whenever the dictionary changes (`delta.rs:11-15`).
  3. A server that ignores `Range` forces a full download (`range.rs:7-9`); the check path then also downloads in full (`update/mod.rs:227-234`).
  4. A republished release at the same size on a host without a strong ETag can mix two releases; the signature check or, unsigned, the manifest content check refuses the result and a full download follows (`range.rs:366-370`, `update/mod.rs:600-619`).
- **Rough Effort:** Done for the blocks payload. Remaining: a release, a measurement of real delta sizes, and a decision on stipple.
- **Risks & Failure Modes:** The unsigned opt-in (see Rank 1) and the stipple limit above.
- **Target Persona:** Open-source developers distributing via GitHub Releases; end users on metered connections.

### Candidate 3: Cryptographic Runtime Integrity via Embedded Ed25519 Root Signature
- **What it is & Technical Mechanism:** Embed a 64-byte Ed25519 digital signature directly in the manifest header or extended footer. The signature would seal `package_id` (the BLAKE3 hash of the manifest serialized with `package_id` and `footer_hash` zeroed, which covers `prefix_hash` and all payload block hashes but not the footer: `footer_hash` is patched in after `package_id` is computed, `pack.rs:1649-1720`, so footer flags are outside it). At startup `onelf-rt` would check one 64-byte signature [~0.2 ms is an unmeasured estimate; `openssl speed ed25519` on a Ryzen 7 7700 gave about 0.07 ms per verify, which is not the `ed25519-compact` crate onelf uses]. FUSE verifies individual block hashes on demand.
- **Competitor Gap Exploited:** uruntime's signature section is never validated, and other portable binaries are unsigned at runtime.
- **User Value:** Detects accidental or unsophisticated modification. It is not tamper-proof: the verifier and the public key sit in the same file, so an attacker who can rewrite the file replaces both (`footer.rs:208-210`). Authentication needs a key the user obtained elsewhere, which is what `onelf verify --key --sig` already does.
- **Rough Effort:** Small (S). `onelf-rt` already depends on `ed25519-compact` (optional `update` feature, `crates/onelf-rt/Cargo.toml:11,25`), not `ed25519-dalek`.
- **Architectural Fit & Kernel Floor:** Natural fit. Universal compatibility (any kernel).
- **Risks & Failure Modes:** Key rotation must be supported via embedded trusted keyring array.
- **Target Persona:** Enterprise workstations, financial institutions, security-conscious Linux distributions.

### Candidate 4: Unprivileged Native Sandboxing via Landlock LSM and Seccomp-BPF
- **What it is & Technical Mechanism:** In-process, unprivileged application sandboxing implemented directly within `onelf-rt`. Before executing the entrypoint in `launch.rs`, `onelf-rt` parses a declarative `[sandbox]` section in `onelf.toml`:
  1. Calls `landlock_create_ruleset()` and `landlock_restrict_self()` (Linux 5.13+ `[verified]`) to restrict filesystem access to specific paths (e.g. read-only `$HOME`, write-only `~/.config/app`). Landlock TCP rules need Linux 6.7+.
  2. Compiles a Seccomp-BPF filter to filter the `TIOCSTI` ioctl request (an ioctl argument, not a syscall), process operations such as `clone3` (return `ENOSYS`), or socket creation. See `workstreams/F-feature-ideas.md` 2.2 for the `no_new_privs`, filter-inheritance and FUSE-rung constraints.
- **Competitor Gap Exploited:** Offers filesystem and syscall confinement without bwrap or portals. The "massive overhead" of Flatpak is not measured here.
- **User Value:** Filesystem-and-syscall confinement, weaker than Flatpak's namespace-based sandbox: Landlock gives no private mount view, PID or IPC namespace and no D-Bus mediation. "Flatpak-grade" and "zero startup latency" in the first edition were overclaims. The project currently states sandboxing is out of scope (`docs/guide/introduction.md`).
- **Rough Effort:** Medium (M) [the ~800-line figure is an unmeasured estimate; crate availability was not checked].
- **Architectural Fit & Kernel Floor:** Natural fit. Requires Linux 5.13+ (gracefully degrades to unconfined on older kernels with warning).
- **Risks & Failure Modes:** Over-restricting file access breaks apps. Mitigated by opt-in manifest declarations and `--unconfined` flag.
- **Target Persona:** Security engineers, enterprise desktop users, privacy advocates.

### Candidate 5: Built-in SBOM (CycloneDX/SPDX) and SLSA Supply-Chain Provenance
- **What it is & Technical Mechanism:** Native storage and introspection of supply-chain metadata inside the container. `onelf build` generates and embeds a zstd-compressed CycloneDX / SPDX JSON inventory (spec versions not checked against current releases) of all bundled packages, shared libraries, licenses, and source repositories into a dedicated manifest section (`.onelf/sbom.json.zst`). Introduces `onelf sbom <binary>` and `onelf provenance <binary>`.
- **Current state:** sysroot builds already record the resolved package name/version list in `.onelf/provenance.toml`, printed by `onelf info` (`docs/guide/sysroot.md`), so the candidate is largely a CycloneDX/SPDX export of existing data plus coverage for host-scan builds.
- **Competitor Gap Exploited:** The first edition's "neither AppImage nor Flatpak bundles SBOMs" was not checked and is unverified.
- **User Value:** Instant vulnerability scanning and regulatory compliance (EU Cyber Resilience Act, US Executive Order 14028).
- **Rough Effort:** Small (S).
- **Architectural Fit & Kernel Floor:** Natural fit. Pure metadata format addition. Universal kernel compatibility.
- **Risks & Failure Modes:** Size increase (~50-200 KB compressed is an unmeasured estimate).
- **Target Persona:** Enterprise procurement, DevSecOps teams, open-source compliance officers.

### Candidate 6: Service Bundles & Multi-Process Micro-Init Supervision
- **What it is & Technical Mechanism:** A built-in process supervisor inside `onelf-rt` that orchestrates multi-process server applications (e.g. Miniflux + PostgreSQL; Gitea + Redis) from a single binary. It invokes `prctl(PR_SET_CHILD_SUBREAPER, 1)` (`linux/prctl.h` **[verified]**) to adopt orphaned processes, spawns declared service workers, manages shared IPC sockets in tmpfs, propagates POSIX signals (`SIGTERM`, `SIGINT`), handles automatic restarts, and supports systemd socket activation (`LISTEN_FDS`).
- **Current state:** onelf already ships exactly this example without a supervisor: `docs/guide/examples/miniflux.md` builds a ~70 MB `miniflux.onelf` that starts a private PostgreSQL, initialises it, runs migrations, serves HTTP and shuts PostgreSQL down, orchestrated by a shell wrapper entrypoint. What a built-in supervisor would add is robustness (signal propagation, restarts, orphan reaping), not the capability. Note the memfd rung ends in `execve`, so a resident supervisor needs another rung.
- **Competitor Gap Exploited:** The first edition's claim that Flatpak and AppImage "fail on multi-process server daemons" is unsupported. Rootless container runtimes exist, so "Docker requires root daemons" is also too strong.
- **User Value:** Cleaner lifecycle handling for single-file server bundles.
- **Rough Effort:** Medium (M). ~1,200 lines of Rust in `onelf-rt`.
- **Architectural Fit & Kernel Floor:** Linux 3.4+ for `PR_SET_CHILD_SUBREAPER`; 5.3+ if `pidfd_open` is used (as the mitigation below does).
- **Risks & Failure Modes:** Zombie process leaks if supervisor fails. Mitigated by `pidfd` tracking (Linux 5.3+).
- **Target Persona:** Self-hosters, homelab enthusiasts, enterprise edge-device deployers.

### Candidate 7: Developer Deep Inspection, Semantic Diffing, and OSV Security Auditing
- **What it is & Technical Mechanism:** A suite of CLI subcommands in `onelf`:
  - `onelf inspect <app.onelf>`: Visualizes the ELF dependency graph (`DT_NEEDED`), inspects host GPU symbol version interop, and generates launch profiles.
  - `onelf diff <v1.onelf> <v2.onelf>`: Compares two bundles at the binary block level, highlighting changed `.so` files, added symbols, and compressed size delta.
  - `onelf audit <app.onelf>`: Parses the embedded SBOM against the Open Source Vulnerability (OSV.dev) API and flags known CVEs.
- **Current state:** onelf already has `info`, `list`, `extract` and `verify` subcommands and `onelf-rt` has a resolver report (`docs/guide/inspecting.md`, `crates/onelf/src/main.rs`); `diff`, `audit` and the SBOM-based CVE lookup would be new.
- **Competitor Gap Exploited:** "Opaque black boxes" is not true of onelf itself; for AppImages, `--appimage-extract` exists but no inspection tooling was surveyed here [unverified].
- **User Value:** Dramatically speeds up developer debugging and packaging iteration.
- **Rough Effort:** Small to Medium (S-M).
- **Architectural Fit & Kernel Floor:** Natural fit. Operates entirely in the developer CLI (`crates/onelf`).
- **Risks & Failure Modes:** Dependency on network access for live CVE lookups.
- **Target Persona:** Package maintainers, CI/CD pipeline engineers, security auditors.

### Candidate 8: OCI / Container Registry Distribution (`onelf push` / `onelf pull`)
- **What it is & Technical Mechanism:** Distribute `.onelf` binaries through standard OCI container registries (GitHub Container Registry `ghcr.io`, Docker Hub, Quay, AWS ECR) using the `artifactType` support of the OCI image and distribution specs v1.1 (the separate `oci artifacts` repository is not the current mechanism) [not re-checked against the spec text]. `onelf push <binary> ghcr.io/org/app:v1.0` uploads the binary with custom media types (`application/vnd.onelf.package.v2`). `onelf pull` streams and downloads it.
- **Competitor Gap Exploited:** Leverages existing high-availability enterprise container storage without requiring bespoke package hosting.
- **User Value:** Seamless integration with enterprise software distribution pipelines and container registries.
- **Rough Effort:** Medium (M). The `oci-distribution` crate's last crates.io update was 2024-03-27; its successor is `oci-client` (0.18.0 on crates.io, queried 2026-10-19).
- **Architectural Fit & Kernel Floor:** Natural fit. Pure transport-layer integration.
- **Risks & Failure Modes:** Authentication and registry quota management.
- **Target Persona:** Cloud-native software vendors, enterprise release managers.

### Candidate 9: Lazy HTTP-Range Streaming Execution (Experimental)
- **What it is & Technical Mechanism:** Launch an application when only 5-10% of its payload has been downloaded (runtime stub + manifest + startup prefetch blocks). When the application requests unpopulated blocks, `onelf-rt` FUSE server intercepts read requests and fetches missing 64 KiB blocks over HTTP on demand.
- **Competitor Gap Exploited:** Eliminates the download barrier for massive applications (games, CAD suites).
- **User Value:** Instant app launch over the internet without waiting for 1-5 GB downloads.
- **Rough Effort:** Large (L).
- **Architectural Fit & Kernel Floor:** Awkward. Requires handling network dropped connections inside FUSE VFS read handlers (which causes application freezes if packets drop).
- **Risks & Failure Modes:** High failure rate on flaky mobile connections; severe latency spikes during dynamic linking.
- **Strategic Verdict:** **Defer / Experimental.**

### Candidate 10: Multi-Architecture Universal Fat Bundles (Polyglot Trampoline)
- **What it is & Technical Mechanism:** Bundle both `x86_64` and `aarch64` binaries and sysroots into a single universal executable. Because the Linux kernel ELF loader rejects foreign-architecture ELF headers with `ENOEXEC` [stated from knowledge of `fs/binfmt_elf.c`; not re-read here], this would need a shell script polyglot prefix that inspects `uname -m`, writes the native ELF stub to `memfd_create`, and executes it.
- **Competitor Gap Exploited:** Mimics macOS Universal 2 binaries.
- **User Value:** Single download link for both PC and ARM laptops (Asus, Lenovo Snapdragon, Raspberry Pi).
- **Rough Effort:** Large (L).
- **Architectural Fit & Kernel Floor:** Breaks core architectural invariants. Doubles the binary size for all users and requires shell interpretation.
- **Strategic Verdict:** **Reject.** Violates the Linux philosophy of architecture-specific distribution.

## 6. Recommended 3-Feature Roadmap and Deliberate Non-Goals

### 6.1 The Unbeatable Identity: The Cohesive 3-Feature Roadmap

To dominate the portable Linux packaging landscape, `onelf` should not attempt to mimic Flatpak or Docker. Instead, it must double down on its unique identity: **The Cryptographically Sealed, Self-Sandboxing, Zero-Overhead Self-Updating Single Binary**.

The following three features form a tightly integrated, cohesive technical triad:

```
THE UNBEATABLE TRIAD:
┌────────────────────────────────────────────────────────────────────────┐
│ Feature 1: Direct-Release Delta Updates (HTTP Range on Block Manifest) │
│   → BUILT at HEAD (PR #41), unreleased; needs measurement + release.   │
├────────────────────────────────────────────────────────────────────────┤
│ Feature 2: Embedded Ed25519 Root Signature for Runtime Integrity       │
│   → Detects modification at launch (not authentication; see Cand. 3). │
├────────────────────────────────────────────────────────────────────────┤
│ Feature 3: Native Unprivileged Landlock + Seccomp-BPF Sandboxing       │
│   → Landlock/seccomp confinement without Bubblewrap or portals.        │
└────────────────────────────────────────────────────────────────────────┘
```

#### Feature 1: Direct-Release Delta Updates (HTTP Range on Native Manifest) - built at HEAD
- **Status:** Implemented in PR #41 and unreleased (see Candidate 2). Maintainers upload the binary plus a detached `.sig` (or the binary alone under the unsigned opt-in) instead of binary, `.zsync` and `.zsync.sig`. What is left of this feature is a release, a measurement of real delta sizes against `zsync`, and a decision about stipple payloads, which only delta-update when stored uncompressed.

#### Feature 2: Embedded Ed25519 Root Signature for Runtime Integrity
- **Synergy:** Would let Feature 1 verify a release without a separate signature fetch. A signature over `package_id` alone leaves footer flags unsigned (see Candidate 3), and an in-file signature does not authenticate against an attacker who can rewrite the file. Timing (~0.2 ms) is an unmeasured estimate.

#### Feature 3: Native Unprivileged Landlock + Seccomp-BPF Sandboxing
- **Synergy:** Declarative filesystem and syscall confinement from the runtime. It gives a weaker posture than Flatpak (no mount, PID or IPC namespaces, no D-Bus mediation) and its startup cost was not measured; the "sub-millisecond" claim in the first edition is removed.

### 6.2 Explicit List of What to DELIBERATELY NOT DO (And Why)

1. **DO NOT emulate ancient Linux kernels (<3.8) via ptrace/syscall translation:**
   - *Why:* `Anylinux-sharun` achieves its 2.6.17 floor (x86_64 only) with about 2.8k lines of ptrace/seccomp emulation (`kernel_compat.rs` 1,799 lines plus `emulated_syscalls.rs` 976). The layer is off unless the kernel is older than 4.0 or lacks `statx`; on 3.5 and later it uses seccomp-bpf so only the emulated syscalls trap, and below 3.5 every syscall is ptraced, which upstream calls much slower. No measurement exists. Maintenance cost and "dead platforms" are this report's opinion.
2. **DO NOT build a centralized runtime or daemon system (Avoid the Flatpak Trap):**
   - *Why:* Flatpak already owns centralized multi-gigabyte runtimes and systemd daemon integration. Mimicking this destroys `onelf` greatest competitive advantage: zero-install, single-file portability that runs anywhere from a USB drive or terminal pipeline.
3. **DO NOT build multi-architecture universal fat binaries:**
   - *Why:* Doubling bundle size to package x86_64 and aarch64 in one file harms 99% of users who only need one architecture. Architecture-specific downloads (`app-x86_64.onelf`, `app-aarch64.onelf`) remain the standard, optimal approach on Linux.
4. **DO NOT depend on XDG Desktop Portals for CLI applications:**
   - *Why:* Portals need D-Bus (the systemd scope is optional and fails soft in Flatpak). "Severe latency" is unmeasured. Landlock gives kernel-enforced path confinement without a portal daemon but does not mediate D-Bus or other services.

## 7. Open Questions That Only the Author (Rabindra Dhakal / QaidVoid) Can Answer

The following deep architectural questions require authorial intent and design decisions from `QaidVoid`:

1. **Format Versioning & Trailer Expansion:**  
   *The fixed 76-byte footer (`crates/onelf-format/src/footer.rs:162-184` [verified]) currently has no dedicated space for an Ed25519 signature (which requires 64 bytes) or public key hash, and `package_id` does not cover the footer (`pack.rs:1649-1720`), so a signed digest must also include `footer_hash`. Does format version 3 intend to expand the fixed footer to 140 bytes, or should cryptographic signatures reside inside the compressed manifest header?*
2. **Deterministic Sysroot Locking:**  
   *`onelf-sysroot` resolves against whatever sysroot image the recipe materializes; since v0.4.0 the archive can be pinned by BLAKE3 hash and provenance is recorded. Is the planned path toward bit-for-bit reproducibility for pinless recipes an `onelf.lock` capturing exact resolved versions, or mandatory archive pinning?*
3. **Mesa and OpenGL Philosophy for Desktop Apps:**  
   *`onelf` resolves host GPU drivers via symbol version superset comparison (`resolve.rs`); since v0.4.0 it can also fetch the recipe's pinned GL build when the host has none (`launch.rs:421-432`). Pinless packages on minimal or headless hosts still fail. Should GL pinning be encouraged in documentation and recipes, or is there an appetite for a built-in debloated fallback Mesa bundle (similar to Anylinux)?*
4. **Sandboxing Stance:**  
   *Does `onelf` view sandboxing (e.g. Landlock LSM) as a core responsibility of the single-file runtime, or should security isolation remain the strict domain of external container tooling (`bwrap`, Docker)?*
5. **Ecosystem Registry:**  
   *Is the long-term vision for `onelf` distribution centered on standalone GitHub Releases, or is there interest in establishing a centralized/federated registry (e.g. via OCI registries or a dedicated index like PkgForge/soarpkgs)?*
6. **Stipple as the default payload:**
   *A stipple payload is smaller and, per the author, faster to start (measurements here cover size only, `measurements/README.md`), but a compressed one cannot delta-update and `--dict` does not apply. Is the intended end state stipple-by-default with stored images for frequently updated packages, or does the blocks payload stay the default for updatable packages? Is the 364 KB-tree result (stipple larger than blocks) a fixed per-image overhead you expect to shrink?*
7. **Unsigned updates:**
   *The unsigned opt-in (HEAD) trusts the release server completely and warns on every update. Is it meant for CI and internal channels only, and should `onelf info` or `--onelf-doctor` flag it more loudly than a line in the update path?*
