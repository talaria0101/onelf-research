## 2. Detailed Technical Breakdown of Top Failures

### 2.1 The FUSE2 Dependency Crisis
- **The Shift:** In Ubuntu 22.04 LTS, Canonical demoted `fuse`/`libfuse2` from main in favor of `fuse3` and dropped libfuse2 from the live ISO; the bug was closed Won't Fix for the Ubuntu desktop, while some flavors (Xubuntu, Kubuntu, Ubuntu Budgie, Ubuntu Studio) added libfuse2 back [Launchpad Bug #1965636, verified]. Package indexes: focal `libfuse2` is in main, priority standard; jammy `libfuse2` is in universe, priority optional [verified]. In Debian 12 (Bookworm) `ntfs-3g` depends on `fuse3` where bullseye's depended on `fuse`, and `libfuse2` is priority optional in both releases [verified: packages.debian.org, Packages index]. That Debian 12 desktop installs lack libfuse2 is [inferred], not checked.
- **System Breakage:** AppImages whose type 2 runtime links libfuse2 fail on stock Ubuntu 22.04+ without libfuse2 with:
  `dlopen(): error loading libfuse.so.2` [verified: AppImageKit #1120 and Launchpad #1965636 quote it].
  On Ubuntu 22.04, `apt-get install fuse` proposes to remove `fuse3`, `xdg-desktop-portal` and `xdg-desktop-portal-gtk` (a prompt, shown before confirmation) [AppImageKit Issue #1120, verified; the thread does not show a broken desktop session, and `gnome-shell` is not in the removal list].
- **Workarounds & New Failures:**
  - Running `--appimage-extract-and-run` decompresses the full image to `/tmp`, using disk (or RAM where /tmp is tmpfs) in proportion to the image's uncompressed size; the extraction directory is `<TMPDIR or /tmp>/appimage_extracted_*` [verified: type2-runtime `runtime.c:1495-1609`; no size figure measured].
  - Software mounting AppImages via `unshare(CLONE_NEWUSER)`, a long-open AppImageKit proposal (#389, port under way in type2-runtime PR #137) and shipped in `uruntime`, is expected to fail on **Ubuntu 24.04 LTS**, which defaults `kernel.apparmor_restrict_unprivileged_userns = 1` [sysctl name confirmed in Ubuntu documentation; the default of 1 on 24.04 is taken from secondary sources; the runtime breakage is [inferred], no tracker entry was found].

### 2.2 Glibc Version Mismatches
- **Forward Incompatibility:** Glibc enforces strict symbol versioning (`.gnu.version_r`). If an executable is built against glibc 2.38 (e.g. calling `strlcpy`, versioned `GLIBC_2.38`), running it on an older host with glibc 2.35 produces a fatal dynamic linker abort before entering `main()` [verified].
- **Why Bundling Glibc Breaks AppImages:**
  Bundling `libc.so.6` in an AppImage and resolving it ahead of the host copy is expected to corrupt the dynamic linker internal state (`_rtld_global`), cause dual-libc TLS clashes when `dlopen()`ing host graphics drivers, and cause segmentation faults in NSS resolver libraries [inferred mechanism; evidence is AppImageKit Issue #1078 (open): `libc.so.6` copied into the extracted tree, then `GLIBC_2.30 not found (required by libselinux.so.1)` and `stack smashing detected`, verified; `LD_LIBRARY_PATH`, `_rtld_global`, TLS and NSS are not mentioned in the issue and are [inferred]].
- **Reverse Incompatibility:**
  - Glibc 2.36 stopped emitting `DT_HASH` in glibc's own shared objects (commit `e47de5cb`, "Do not use --hash-style=both for building glibc shared objects", in 2.36 and not in 2.35 [verified: GitHub compare API, 2.36 contains the commit, 2.35 does not]), and Easy Anti-Cheat then failed to load in Proton games [Valve Proton Issue #6051 (open), verified: the issue body names glibc 2.36 and the comments discuss EAC requiring `DT_HASH`].
  - Glibc 2.34 added `clone3()` use (`sysdeps/unix/sysv/linux/clone-internal.c` exists at tag glibc-2.34, not at 2.33); seccomp filters that returned `EPERM` for it instead of `ENOSYS` broke fork/thread creation inside containers (`getaddrinfo() thread failed to start`) [Moby Issue #42680, verified; the report was against a Fedora rawhide image on a Fedora 34 host, before glibc 2.34 was released].

### 2.3 GPU / Mesa / Hardware Acceleration Breakage
- **Mesa ABI Mismatch:** If an AppImage bundles an older `libdrm_amdgpu.so.1` or `libglapi.so.0`, and the application loads a host DRI driver, the host driver can fail with an undefined symbol (`amdgpu_va_get_start_addr`) and the application aborts [FreeCAD Issue #13182 (closed; fixed in weekly builds), verified: the original report is FreeCAD 0.21.2 AppImage on an Intel Iris Xe laptop, failing on `/usr/lib/dri/swrast_dri.so: undefined symbol: amdgpu_va_get_start_addr`; a commenter's `LD_PRELOAD` of the host `libdrm_amdgpu.so` fixes it. The issue does not state which bundled library is stale and does not mention `libglapi.so.0` or `radeonsi_dri.so` as the failing driver; that mechanism is [inferred]. An earlier edition cited #960, which is an unrelated stylesheet PR]. 
- **NVIDIA Proprietary Driver Lock:** In Flatpak, when the host system updates its NVIDIA graphics driver, the kernel module updates to (illustrative) version `550.XX` while the running Flatpak still has extension `535.YY` mounted. The driver aborts with:
  `API mismatch: the NVIDIA kernel module has version 550.XX, but this NVIDIA driver component has version 535.YY` [reported; no flatpak issue tracker entry documents the API-mismatch text - an earlier edition cited #3184, which is an unrelated 2019 OpenGL-extension bug. The matching mechanism that exists to prevent this scenario is verified: `flatpak-utils.c:534` reads `/sys/module/nvidia/version`, and `flatpak_get_gl_drivers()` (`flatpak-utils.c:517`) returns `nvidia-<ver with dots as dashes>`, which is matched against extension basenames for `active-gl-driver` extensions (`flatpak-utils.c:1666-1675`). The extension ID prefix `org.freedesktop.Platform.GL` comes from runtime metadata, not from this source.]

### 2.4 Wayland & Desktop Integration
- **Blurry Fractional Scaling:** Electron apps defaulted to X11/XWayland at the time of the report (2021), rendering blurry under fractional scaling unless launched with `--enable-features=UseOzonePlatform --ozone-platform=wayland` (Electron 12+) [shiftkey/desktop Issue #591, "Support fractional scaling" (closed), verified; the issue concerns GitHub Desktop for Linux generally, is not AppImage-specific, and one commenter reports crashes with those flags; current Electron/Chromium defaults were not checked. An earlier edition cited #3060, which does not exist]
- **Taskbar Icon Disconnect:** Wayland compositors map taskbar icons using `app_id` (matching the `.desktop` file name). Because standalone binaries lack registered `.desktop` files, titlebar and Alt-Tab icons can fall back to generic placeholders on Wayland [AppImageKit Issue #1434 (open), reported: on KDE Wayland the taskbar and menu icons were correct and only the corner and Alt-Tab icon were generic; copying the `.desktop` file and icons to the host fixed it for the reporter].
- **Container Leaks:** `AppImageLauncher`'s `binfmt_misc` registration leaks into Docker containers and causes AppImages to fail to launch inside them [TheAssassin/AppImageLauncher Issue #407 (open), verified title and body; LXC, ELF interception and CI runners are not in the issue].

### 2.5 Sandboxing Friction
- **AppImage:** Zero containment by default. An AppImage runs with the invoking user's full authority, so it can read `~/.ssh`, GPG keys and browser credential stores [inferred from the absence of containment]. That enterprise security teams ban AppImages is [reported] without a cited source.
- **Flatpak Over-Sandboxing:** Strict portal file pickers break multi-file workflows (the issue names video playback with external subtitles, audio/video authoring projects with assets, and IDEs needing a whole project folder; VLC and Blender are not named in the issue) [flatpak/xdg-desktop-portal Issue #463, verified - title "Portal to open file and neighbouring files"; the repo moved from the `xdg` org to `flatpak`, where an earlier edition's link 404s].
